# Revisions that have been released, and the parent each was released with.
#
# One line per revision: <revision> <down_revision>.
#
# This exists because alembic records only where a database is now, never the
# path it took. A migration slotted in behind an existing one therefore runs
# on a database built from scratch and never on a database already past it --
# alembic computes 028 -> 029 and does not walk backwards. The table is never
# created, head is still reported, and the first symptom is the code that uses
# the table failing in production.
#
# That happened here: processing_jobs was added as revision 021, ahead of the
# migration already holding that number, which was renamed to 021a to make
# room. Fresh databases got the table. Every existing one did not.
#
# No test of the current chain can catch that, because the chain is perfectly
# valid -- what is wrong is its relationship to databases that already exist.
# This file is that missing history.
#
# Adding a migration: append one line. Its parent must be the current last
# line, so it lands at the end of the chain, which is the only place every
# database is guaranteed to pass through.
#
# Editing or removing a line means changing the identity of a migration that
# databases have already run. There is almost never a good reason, and the
# friction is the point.
#
